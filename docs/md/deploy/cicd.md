# CI/CD

本文说明微服务的持续集成与持续交付流程，前端的发布见前端仓库 [nilo-webpage](https://github.com/avaNeon/nilo-webpage) 的 `docs/md/deploy`

> 注意：文中的 **GitHub 云服务器**指 GitHub Actions 执行任务时临时分配的运行环境； **服务器**指运行 Nilo 的机器

## 概览

| 阶段       | 触发方式                  | 现状                                                         |
|------------|---------------------------|--------------------------------------------------------------|
| CI         | 每次 push 与 Pull Request | 已完成：编译打包；推送到 master 时构建并推送镜像；测试待补充 |
| CD         | 手动触发                  | 已完成：镜像随提交自动产出，发布时只负责部署                 |
| 部署后检查 | 发布完成后自动执行        | 已完成：冒烟测试，检查服务可响应、接口文档不可访问           |

### 结构

```
推送到 master ──▶ CI（编译打包、构建并推送镜像）
手动触发 ──▶ prepare（校验镜像）──▶ server（拉取并重启）──▶ verify（冒烟测试）
```

两部分通过镜像仓库（GHCR）衔接：CI 负责产出镜像，发布只使用镜像，不再构建。

### CI

- 每次 push 与 Pull Request 自动编译并打包。
- 目前跳过本地测试（这些测试仅在本地开发时使用），单元测试与集成测试有待补充。
- 推送到 master 时，编译通过后为每个服务构建镜像并推送到镜像仓库，与发布无关。PR 与其他分支只做编译检查，不推送镜像。
- master 上的运行排队依次执行，保证 `latest` 始终指向最后一次提交。

### CD

- 持续交付（Continuous Delivery）：每次提交到 master 都自动产出可直接部署的镜像，部署时机由人工决定。
- 发布只负责校验镜像、拉取并重启，不再构建。同一时间只运行一个发布任务。
- 后续：支持按提交号部署与回滚。

### 部署后检查

发布完成后自动执行冒烟测试，详见 [security.md](security.md)。

## 操作

先把代码推送到 master 并等待 CI 完成，再在 GitHub Actions 中手动触发 Deploy 工作流，选择操作：

| 操作    | 说明                                                    | 涉及的任务              |
|---------|---------------------------------------------------------|-------------------------|
| deploy  | 校验镜像，发布并拉取所选服务                            | prepare、server、verify |
| up      | 启动全部容器，先启动中间件/DB，待其初始化后再启动微服务 | server、verify          |
| down    | 停止全部容器，先微服务，后中间件/DB                     | server                  |
| restart | 重启全部容器                                            | server                  |
| check   | 仅执行部署后检查，不部署                                | server                  |

## 构建镜像（CI）

- 所有服务共用一个 Dockerfile，通过构建参数指定模块。
- 镜像同时打 `latest` 与提交号 (sha) 两个标签，后者用于追溯版本。
- 镜像中不包含大部分配置，这些配置由 nacos 管理。
- 镜像内置 FFmpeg（转码与缩略图通过命令行调用它，需要装在容器里，而不是宿主机上）。构建时会检查其可用，缺失则构建失败。
- 每次推送到 master 都构建全部服务的镜像，不区分改动了哪个模块。

## 发布流程

下面以 **deploy** 操作为例

```
手动触发 ──▶ prepare ──▶ server ──▶ verify
```

| 任务    | 运行位置        | 作用                                             |
|---------|-----------------|--------------------------------------------------|
| prepare | GitHub 云服务器 | 汇总所选服务，校验这些服务在当前提交的镜像已存在 |
| server  | 服务器          | 拉取镜像、启动所选服务                           |
| verify  | 服务器          | 部署后检查，确认接口文档不可访问                 |

### prepare

确认所选服务在当前提交的镜像已经存在于镜像仓库。找不到通常是 CI 还没跑完，或触发时选择的不是 master 上的提交，此时任务失败，不会部署。

### server

GitHub 云服务器通过 SSH 向服务器发送一条指令（如 `deploy nilo-web nilo-storage`
），由服务器上的**部署脚本**解析并执行。该连接的权限受到限制，**限制**与**部署脚本**详见 [security.md](security.md)。

服务器拉取的是 `latest`，即 master 上最近一次 CI 构建的镜像。

### verify

`deploy` 或 `up` 完成后自动执行：`deploy` 操作下仅检查本次发布的服务，`up`
操作则检查全部服务。检查失败时任务标记为失败，已部署的服务不自动回滚。**检查内容**详见 [security.md](security.md)中的**部署脚本**的 **check 操作**。

## 新增微服务的扩展方式

1. 模块可打包为可执行 jar（Spring Boot Maven 插件）。
2. 在服务器部署脚本的服务清单中登记。
3. 在微服务的 compose 文件中添加服务定义。
4. 在 `ci.yml` 的服务清单（构建镜像）和 `deploy.yml`（勾选项）中添加对应项。

## 取舍

| 决定             | 原因                                                   | 代价                                                         |
|------------------|--------------------------------------------------------|--------------------------------------------------------------|
| 手动触发         | 发布时机由人工控制                                     | 多一次操作                                                   |
| 镜像在 CI 中构建 | 每次提交都有可部署的镜像，构建与部署解耦，发布只需拉取 | 每次推送到 master 都构建全部服务，占用构建额度与镜像仓库空间 |
| 按服务选择性发布 | 只重启有变更的服务                                     | 新增服务需同步维护服务清单                                   |
| 共用 Dockerfile  | 各服务构建方式一致，避免重复                           | 运行参数需在 compose 中单独配置                              |
| 配置外置于 Nacos | 同一镜像可用于不同环境，镜像不含密钥                   | 依赖配置中心                                                 |
| 镜像设为公开     | 服务器拉取镜像无需认证                                 | 无（项目开源，镜像内容本就公开）                             |

## 当前的局限

- CI 仅编译，不运行测试。
- 服务器拉取 `latest`，只能部署 master 上最近一次构建的镜像，不支持按提交号部署，因此也无法回滚到旧版本。
- 不支持自动回滚，部署后检查仅在失败时告警。
- 重启期间服务短暂不可用。
