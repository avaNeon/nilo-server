# 部署安全

本文说明服务端的 CI/CD 涉及的权限控制，以及部署后的安全检查

> 注意：文中的 **GitHub 云服务器**指 GitHub Actions 执行任务时临时分配的运行环境； **服务器**指运行 Nilo 的机器

## 目标

发布时，GitHub 云服务器需要登录服务器并执行部署，因此必须提供对应部署账户的 SSH 私钥以连接服务器。

目标是遵循最小权限原则： 即使私钥泄露，攻击者也只能执行预先允许的部署操作，无法获得服务器的其他权限。

## 权限限制

部署使用专用账户，并通过四层机制限制其权限：

| 层                | 机制                                                         | 限制内容                                                             |
|-------------------|--------------------------------------------------------------|----------------------------------------------------------------------|
| 1. 专用账户与密钥 | 独立的部署账户，公钥认证，私钥仅存放于 GitHub Secrets        | 与日常登录的账户和密钥完全分离                                       |
| 2. SSH 强制命令   | 公钥在 `~/.ssh/authorized_keys` 中绑定 `command=` 选项       | 该密钥登录后只能运行指定的部署脚本；禁用交互终端、端口转发、代理转发 |
| 3. 脚本白名单     | 部署脚本只接受预定义的操作与服务名                           | 其余输入一律拒绝；客户端传来的内容仅作参数，不会被当作命令执行       |
| 4. sudo 白名单    | 保证部署账户仅可以管理员身份运行指定的 `docker compose` 命令 | 不能执行其他需要管理员权限的操作                                     |

## 部署脚本

脚本的处理逻辑（简化的伪代码）：

```bash
ALLOWED=(nilo-web nilo-admin ...)       # 服务白名单
读取输入：第一个词为操作，其余为服务名

switch 操作
  deploy:   校验服务名 → 拉取所选服务的镜像 → 启动所选服务
  up:       启动中间件 → 等待其初始化 → 启动全部微服务
  down:     停止微服务 → 停止中间件
  restart:  重启全部容器
  check:    校验服务名 → 执行部署后检查
  其他:     拒绝
```

输入示例：

| 输入                     | 结果                     |
|--------------------------|--------------------------|
| `deploy nilo-web`        | 执行                     |
| `deploy nilo-web;reboot` | 拒绝：服务名不在白名单中 |
| `rm -rf /`               | 拒绝：无法识别的操作     |

## 部署后检查

> 也是冒烟测试

### 目的

验证生产环境下接口文档是否全部阻塞。接口文档会列出全部接口的细节，不应对外开放。

文档在生产环境通过配置关闭（关闭文档接口与页面，并启用 Knife4j 的生产模式）拦截相关路径。这些配置位于
Nacos，而本地配置默认开启文档，因此一旦配置未生效（例如配置中心读取失败），文档就会暴露。该检查用于发现这类问题。

### 方式

发布完成后，对每个服务访问 6 个路径（接口文档数据、Swagger 页面、Knife4j 页面）。只有下列三种响应视为 **已拦截**，其余一律判定为失败：

| 响应                                       | 来源                                       |
|--------------------------------------------|--------------------------------------------|
| HTTP 404                                   | 框架默认的"路径不存在"                     |
| 项目统一的错误 JSON（`status` 为 `error`） | 项目对不存在的路径返回 HTTP 200 与错误信息 |
| Knife4j 的拦截提示                         | 生产模式拦截                               |

对于不存在的路径，此项目采用了全局拦截器处理，HTTP 状态码仍然是 200，此外 Knife4j 的拦截提示会返回：You do not have permission
to access this page

### 执行流程

1. 先等待服务可响应，再开始检查。不要求健康检查为 UP，因为一些不影响业务的依赖组件异常，甚至是在预期中的异常都会使其为 DOWN。
2. `deploy` 仅检查本次发布的服务，`up` 检查全部服务，也可单独执行 `check`。
3. 有任一路径未被拦截，`verify` 任务即标记为失败；已部署的服务不会回滚。
4. 新增检查路径，在脚本的路径清单中添加即可。

## 范围

- 检查目前仅覆盖接口文档可达性。
- 检查在部署之后执行，发现问题时服务已经上线。
- 对外入口（nginx）层面的检查，以及管理端点、内部接口是否对外暴露，尚未覆盖。

管理控制台的访问限制见 [nginx.md](nginx.md)。前端上传账户的权限限制见前端仓库 [nilo-webpage](https://github.com/avaNeon/nilo-webpage) 的 `docs/md/deploy`。
