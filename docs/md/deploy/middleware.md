# 中间件

本文说明中间件与数据库的部署方式

## 概览

9 个组件通过同一份 Docker Compose 文件部署，与微服务的 Compose 文件分开管理。

| 组件               | 镜像                                  | 部署内容                                                   |
|--------------------|---------------------------------------|------------------------------------------------------------|
| MySQL              | 官方                                  | 配置文件、数据、日志挂载                                   |
| Redis              | 官方                                  | 配置文件、数据挂载                                         |
| Elasticsearch      | 自建（官方镜像加中文分词插件 IK）     | 单节点；开启账号认证；词典目录挂载；限制堆大小             |
| RabbitMQ           | 官方（含管理插件）                    | 配置文件、数据挂载                                         |
| MinIO              | MinIO AIStor 版（镜像来自 Quay.io）   | 数据、证书挂载；需申请许可证文件；固定版本；限制运行时内存 |
| Canal              | 官方                                  | 同步规则只读挂载；替换启动脚本以调整 JVM 内存              |
| Nacos              | 官方                                  | 单机模式；配置持久化到 MySQL；开启鉴权；配有健康检查       |
| Seata              | 官方                                  | 文件存储模式；替换配置文件；通过专用环境变量设置 JVM 参数  |
| Sentinel Dashboard | 自建（无官方镜像，用发布的 jar 构建） | 通过环境变量覆盖内存参数                                   |

## 网络与访问

- 所有容器位于同一个 Docker 网络，彼此通过容器名访问。微服务的 Compose 文件以外部网络的方式加入该网络。
- 容器端口只映射到本机回环地址，外部无法直接连接，保证 **安全**。同时也让彼此链接变得方便，因为彼此连接只在机器内部传输数据，可以不用
  TLS 加密
- Nacos、Sentinel Dashboard、Seata 的管理控制台需要能让管理员查看，因此由 nginx 转发，启用 HTTPS 并限制访问
  IP，见 [nginx.md](nginx.md)。

## 启动顺序

```
MySQL ──▶ Nacos（健康检查通过）、Canal ──▶ 微服务
```

- Nacos 数据持久化到了 MySQL ，需要等待后者启动完毕再启动
- 网络由中间件的 Compose 创建，因此必须先启动中间件，再启动微服务；停止时顺序相反，`down` 会删除网络。
- Nacos 配置了健康检查。Nacos 尚未初始化完成时，微服务读到的是空配置，且不会报错，配置顺序见 [config.md](config.md)。且微服务在另一个
  docker-compose.yaml 中，无法使用 `depends_on` 等待中间件，因此发布流程中的 `up`
  操作会在两者之间等待固定时间，见 [cicd.md](cicd.md) 的“操作”章节。
- 容器设置了自动重启策略，挂了会自动重启。微服务在中间件初始化完毕前启动导致启动失败的情况下，这个配置可以让微服务自动重试。

## 数据持久化

数据目录挂载到宿主机，容器重建后数据保留。

| 组件          | 挂载内容                         |
|---------------|----------------------------------|
| MySQL         | 数据目录、日志、配置文件         |
| Redis         | 数据目录、配置文件               |
| Elasticsearch | 数据目录、分词词典               |
| RabbitMQ      | 数据目录、配置文件               |
| MinIO         | 对象数据目录、证书（不配不给用） |
| Seata         | 会话存储目录、配置文件           |
| Nacos         | 仅日志，配置存储在 MySQL 中      |

Canal 与 Sentinel 不挂载数据目录。Sentinel 的规则存放在 Nacos 中。

## 资源限制

> 对于小规模部署而言，一个很现实的问题是，怎么在一台性能不高的机器上尽可能地榨出更多的资源以满足多达十几种的软件的使用。
> 因此我们必须尽可能地限制每个程序的资源使用，尤其是内存。我们并不需要大量CPU操作，而磁盘资源比较廉价，所以我们需要限制每个软件的内存使用。

服务器内存有限，因此：

- 每个容器都设置内存上限，避免单个组件耗尽整机内存。
- Java 组件（Nacos、Seata、Sentinel、Elasticsearch、Canal）同时限制堆大小，使堆与非堆（元空间、线程栈、直接内存）之和不超过容器上限。
- 所有容器的内存上限之和低于机器内存，为宿主机与 nginx 留出余量。
- 微服务同样设置内存上限，如果内存上限小于2G，请使用串行垃圾回收器（SerialGC）而非 JDK 17 默认的 G1。G1
  依赖多线程与额外的数据结构，内存开销更大；串行回收器占用最小，代价是回收时暂停全部业务线程。微服务的堆较小，暂停时间相对较短，可以接受。
- 如果内存还是不够，就在服务器层面设置 swap 防止 OOM。

> 注意：Seata 的启动脚本会自动执行 java -version 并解析其输出。JAVA_TOOL_OPTIONS 会使 JVM
> 每次启动多输出一行提示，导致解析失败，因此应改用脚本识别的专用环境变量（如 JVM_XMX）。

## 账号与认证

- Nacos、Sentinel、Seata 的控制台各自设置独立账号；Nacos 开启鉴权，客户端连接时需提供账号。
- Nacos 使用独立的数据库账号；Elasticsearch 开启认证，应用使用受限账号，不使用内置超级用户。
- Compose 文件中包含账号密码，仅保存在服务器上，不纳入代码仓库。

## 注意

- 中间件不纳入 CI/CD，因为我们几乎不会手动改变版本或者镜像，如需要升级时需手动修改镜像版本并重启。
- **这些配置**仅适合在 **资源受局限的的情况下小规模部署**，不具有很好的容灾、吞吐、可用能力。这不代表这个项目的设计存在漏洞，而是
  资源受限下的 **取舍**。
