# 对外访问

本文说明 nginx 如何对外提供网站与接口，以及管理控制台的访问限制

## 概览

nginx 部署在宿主机，是唯一的对外入口。各站点使用独立的域名与证书：

| 站点           | 内容                                        | 访问限制      |
|----------------|---------------------------------------------|---------------|
| 主站           | 用户端前端的静态文件；业务接口与 MCP 的转发 | 公开          |
| 后台管理站     | 后台前端的静态文件；后台接口的转发          | 仅指定来源 IP |
| 对象存储       | MinIO 的对象接口，浏览器直接读取图片、视频  | 公开          |
| 对象存储控制台 | MinIO 的 Web 管理界面                       | 仅指定来源 IP |
| 管理控制台     | Nacos、Sentinel、Seata 的 Web 管理界面      | 仅指定来源 IP |

- 证书由 Let's Encrypt 签发，nginx 在宿主机上便于 certbot 续期。
- 主站、后台管理站、对象存储的 HTTP 请求统一 301 跳转到 HTTPS。
- 所有容器端口仅在本机监听，外部无法绕过 nginx 直接访问。

## 主站

### 路由

| 路径            | 去向         | 说明                                          |
|-----------------|--------------|-----------------------------------------------|
| `/api/web/`     | nilo-web     | 用户端接口                                    |
| `/api/comment/` | nilo-comment | 评论                                          |
| `/api/ai/`      | nilo-ai      | AI 问答，流式返回，读超时放宽                 |
| `/sse`、`/mcp/` | nilo-ai      | MCP 服务，`/sse` 是长连接，关闭缓冲并放宽超时 |
| 其余路径        | 静态文件     | 见下文                                        |

转发时去掉路径前缀：`/api/web/foo` 到达 nilo-web 时是 `/foo`。这与前端开发服务器的代理规则一致，因此本地与服务器上前端使用同一套接口路径。

后台管理站同理：`/api/admin/` 转发给 nilo-admin，其余为静态文件。

```nginx
location /api/web/ { proxy_pass http://nilo_web/; }   # nilo_web 是连接池（见下文）；末尾的 / 使前缀被去掉
```

### 内部接口不对外

微服务的 `/inner/` 接口只供服务之间调用。nginx 用一条规则拦截所有形如 `/api/<服务>/inner/...` 的请求，直接返回
404。正则规则的优先级高于前缀规则，因此不会被上面的转发规则放行。

### 流式与长连接

AI 问答使用流式返回，MCP 使用长连接。这些路径的读超时被放宽，`/sse` 额外关闭了代理缓冲，否则内容会被攒满后才发给浏览器。

### 转发请求头

转发给微服务时统一带上原始的 Host、用户的真实 IP、转发链与协议（http/https）。微服务据此获得真实的客户端信息。

请求体大小上限放宽到 50 MB。视频由浏览器直传对象存储，不经过主站。

### 到微服务的连接复用

用户的连接由 nginx 接住，nginx 再通过连接池（`upstream` + `keepalive`）转发给各微服务，不为每个请求新建连接：

- 微服务只需维持少量长连接，不必为每个用户连接分配读写缓冲。压测中，Tomcat 直接承接 5000 条客户端长连接时，仅连接缓冲就占用约
  78 MB 堆内存。
- 避免短连接在 nginx 一侧堆积 TIME_WAIT。nginx 与微服务分布在不同机器上时，短连接会耗尽本地端口。

两端的参数需要配合：

| 参数                 | nginx | Tomcat | 原因                                                                |
|----------------------|-------|--------|---------------------------------------------------------------------|
| 空闲连接超时         | 50 秒 | 60 秒  | 由 nginx 先关闭空闲连接，避免复用一条 Tomcat 刚关闭的连接而返回 502 |
| 单条连接的请求数上限 | 1000  | 1000   | Tomcat 默认 100，池中的连接会被频繁关闭、重建                       |

复用连接还要求转发使用 HTTP/1.1，并清空 `Connection` 请求头。

## 静态文件

前端构建后是静态文件，由 nginx
直接读取，没有前端进程；发布就是替换文件，见前端仓库 [nilo-webpage](https://github.com/avaNeon/nilo-webpage) 的
`docs/md/deploy`。

| 路径          | 策略                                  | 原因                                       |
|---------------|---------------------------------------|--------------------------------------------|
| `/index.html` | 不缓存（`no-cache`）                  | 每次发布都会变，缓存会让用户一直看到旧页面 |
| `/assets/`    | 缓存 30 天，标记不可变（`immutable`） | 文件名带内容哈希，文件一变名字就变         |
| 其余路径      | 找不到文件时返回 `index.html`         | 前端是单页应用，页面地址由前端路由处理     |

文本类资源启用 gzip 压缩。

## 管理控制台的访问限制

后台管理站、Nacos、Sentinel、Seata 与 MinIO 的控制台能直接改动系统，不对公网开放：

- 每个控制台使用独立的子域名与证书。
- nginx 只放行指定的来源 IP（`allow` + `deny all`），其余请求直接拒绝。
- 控制台自身的认证仍然保留（例如 Nacos 开启了登录验证），IP 限制是额外的一层。

## 取舍

| 决定                     | 原因                                                             | 代价                                            |
|--------------------------|------------------------------------------------------------------|-------------------------------------------------|
| nginx 部署在宿主机       | 证书续期简单，静态文件直接由 nginx 读取                          | 配置不在容器编排里，需要单独维护                |
| 独立子域名 + IP 白名单   | 控制台的地址不暴露在主站的路径下，限制规则简单明确               | 每个控制台需要一个域名和证书                    |
| 转发时去掉路径前缀       | 微服务本身不需要知道对外的路径，本地与服务器一致                 | 前缀与服务的对应关系需要在前端和 nginx 两处维护 |
| nginx 到微服务使用连接池 | 微服务的连接数与用户数无关，不堆积 TIME_WAIT，便于拆分到多台机器 | 两端的超时与请求数上限需要配合调整              |

## 当前的局限

- 来源 IP 白名单写在配置里，IP 变化后需手动修改并重载 nginx。
- nginx 层没有做请求限流，接口的限流依赖 Sentinel。
- 部署后检查尚未覆盖 nginx 层：内部接口与控制台是否对外暴露，目前靠配置保证，没有自动检查。
