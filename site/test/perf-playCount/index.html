播放统计压测结果

在三台不同配置的 GitHub 提供的云主机上分别运行一次测试，每台主机上的不同版本的测试都是在相同配置下进行的。

并且，被测机中间件和服务的资源限制和配置与线上相同，压测机用 k6 按固定速率发送请求，每轮结束后把 MySQL、Redis 的播放量增量与放行请求数逐条对账。

由于不同运行分到的硬件不同，相对于比较绝对值来说，比较趋势更为合适。

每次运行 V0→V1→ V2→V3→ V0 对照 同一对机器，对照轮用来估计误差

V0基线

请求线程内依次写 MySQL 和 Redis

V1异步

请求只放入本地队列，每 5 秒聚合为（视频，增量）后经 MQ 异步写入

V2批量

MySQL 每 100 个视频合成一条 UPDATE，Redis 用一次 Lua 脚本写完整条消息

V3当前线上

消费端并行写入 MySQL 与 Redis

01

总体性能

吞吐

放行吞吐 · 次/秒 · 线性 V0 → V0 对照

分析
放行吞吐 = 放行请求数 ÷ 压测时长，虚线为目标速率。吞吐接近目标速率时，数值受目标速率限制，不再反映处理能力的上限。 淡色细线连接第 1 轮与对照轮（二者为同一版本），两点越接近，说明该次运行的重复性越好。

开销

每个放行请求的 CPU 合计ms · 线性

分析
每个放行请求的 CPU = 测试窗口内全部组件消耗的 CPU 秒数 ÷ 放行请求数。窗口包含压测结束后的排空阶段， 因此该指标与压测时长及排空快慢无关，同一次运行内的各版本可直接比较；在对照轮中，其波动小于吞吐。

按组件拆解ms / 请求

分析
将上图的每请求 CPU 按组件拆分，柱顶为合计，图例列出各组件由第一个版本到最后一个版本的变化。

02

生产端性能

服务端响应时间

平均P99 ms · 对数刻度

分析
由 nilo-web 自行统计，不含网络往返，也不含在 nginx 排队的时间。实线为平均值，虚线为 P99（99% 的请求不超过该值）。 纵轴为对数刻度，相邻刻度相差 10 倍。

03

消费端性能

队列积压

条

分析
播放量队列在测试窗口内的消息数峰值。待投递指尚未交付消费端的消息，未确认指已交付消费端、尚未处理完成的消息。

写入完成延迟

秒 · 对数刻度

分析
从压测机收到最后一个响应起，到被测机 MySQL 与 Redis 的播放量不再变化止的时间，即最后一批播放量落库所需的时间。 纵轴为对数刻度，相邻刻度相差 10 倍。

MySQL 每秒查询数峰值

次/秒 · 对数刻度

分析
测试窗口内 MySQL 每秒执行语句数的最大值，含写入监控自身每秒 10 次的查询。纵轴为对数刻度，相邻刻度相差 10 倍。

被测机整机 CPU 平均% · 上限 100

分析
压测期间被测机全部核的平均使用率，包含容器之外的开销（Tailscale、内核收发网络包等）。接近 100% 表示 CPU 已饱和， 此时的放行吞吐即该机器的处理上限；使用率较低而吞吐未达目标速率，则瓶颈位于其他资源。

吞吐倍数（相对第 1 轮）倍 · 线性

分析
各轮放行吞吐 ÷ 第 1 轮放行吞吐。对照轮与第 1 轮为同一版本，其偏离 1 的程度即本次运行的误差范围； 版本之间的差距小于该范围时，不宜据此下结论。
